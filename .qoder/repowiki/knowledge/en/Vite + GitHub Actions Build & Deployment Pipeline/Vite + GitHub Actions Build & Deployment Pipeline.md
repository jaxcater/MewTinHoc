## Build System Overview

The project is a single-package Vite/React SPA with a small Node.js proxy server. There is no Makefile, Dockerfile, or monorepo tooling — the build surface is concentrated in `package.json`, `vite.config.js`, and two GitHub Actions workflows.

## Toolchain

- **Build tool**: Vite 8 (`@vitejs/plugin-react` 6) for the React frontend.
- **Runtime**: Node.js 22 (both CI and the VPS deployment use this version).
- **Package manager**: npm (lockfile `package-lock.json`; CI uses `npm ci`).
- **Linting**: oxlint (`oxlint` v1), invoked via `npm run lint`.
- **Server**: A standalone `server/server.js` process (PM2-managed on the VPS) that serves static files and proxies `/api/botpress` to Botpress Cloud.

## Scripts (`package.json`)

| Script | Command | Purpose |
|---|---|---|
| `dev` | `vite` | Local dev server with HMR |
| `build` | `vite build` | Production build → `dist/` |
| `preview` | `vite preview` | Preview built output locally |
| `server` | `node server/server.js` | Start the Node proxy server |
| `lint` | `oxlint` | Lint source files |
| `export:roadmap` | `node scripts/exportRoadmaps.js` | Export roadmap data to JSON under `LoTrinhDayXich/` and `public/LoTrinhDayXich/` |

There is no test script defined; tests live only under `.agents/skills/security-audit/` as CJS unit tests for security audit coverage validation.

## Vite Configuration (`vite.config.js`)

- `base: '/'` — root-relative asset paths.
- Custom plugin `botpress-backend-api` mounts `botpressMiddleware` at both `/api/botpress` and `/MewTinHoc/api/botpress` during development so the dev server can proxy Botpress requests.
- `build.cssMinify: false` — CSS is left unminified in production builds.
- The React plugin is the only official Vite plugin used.

## CI / Release Flow

Two workflows under `.github/workflows/`:

### `deploy.yml` — GitHub Pages

- Triggered on push to `main` and `workflow_dispatch`.
- Uses `actions/setup-node@v4` with `node-version: 22` and `cache: npm`.
- Runs `npm ci` then `npm run build`.
- Uploads `dist/` via `actions/upload-pages-artifact@v3`.
- Deploys through `actions/deploy-pages@v4` using the `github-pages` environment (requires `pages: write` and `id-token: write` permissions).
- Concurrency group `pages` cancels in-progress deployments.

### `deploy-vps.yml` — VPS Deployment

- Triggered on push to `main`.
- Connects to host `31.97.188.238` as `root` using `appleboy/ssh-action@v1.0.3` with secret `VPS_SSH_KEY`.
- On the remote machine:
  - `git fetch origin main` + `git reset --hard origin/main` (the VPS checkout is treated as a deploy mirror; tracked server-side edits are discarded).
  - Sets PATH to `/www/server/nodejs/v22.22.1/bin`.
  - Runs `npm ci --include=dev` (comment explains Vite lives in devDependencies so full dependency tree is needed to build).
  - Runs `npm run build`.
  - Exports `NODE_ENV=production` **after** install (comment warns it must not be set before `npm ci`).
  - Restarts PM2 process `mewtinhoc` with `pm2 restart mewtinhoc --update-env`.
  - Asserts `test -f dist/index.html` before finishing.

## Build Artifacts

- Frontend SPA: `dist/` directory produced by Vite.
- Favicon ICO: generated by `scripts/buildFaviconIco.cjs`, which reads `public/img/favicon-{16,32,48}.png` and writes `public/img/favicon.ico` as a multi-image Microsoft ICO file (PNG payloads, per the comment's spec notes).
- Roadmap JSON: generated by `scripts/exportRoadmaps.js`, which dynamically imports `src/data/roadmap/csRoadmap.js` and `ictRoadmap.js` and writes `csRoadmap.json` / `ictRoadmap.json` into both `LoTrinhDayXich/` and `public/LoTrinhDayXich/`.

## Conventions Observed

- All runtime dependencies are declared under `dependencies`; build tools (Vite, oxlint) live under `devDependencies`.
- The package is marked `private: true` and `type: module` (ESM source, though some scripts like `buildFaviconIco.cjs` still use CommonJS).
- Versioning is pinned to `0.0.0` in `package.json`; there is no automated version bumping in any script or workflow.
- The VPS deployment does not use Docker or a container image — it performs an in-place `git reset --hard` of the repo and rebuilds from source.
- Environment variables for the production server are injected via PM2's `--update-env` flag rather than being baked into the build.
